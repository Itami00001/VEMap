# VEMAP

## Техническое задание v1.0

**Статус:** базовое техническое задание проекта
**Название:** VEMap
**Тип:** веб-приложение / аналитическая платформа
**География:** Россия
**Основная пространственная единица:** регион
**Основная временная единица:** год
**Язык интерфейса на MVP:** русский
**Целевой срок MVP:** 2–3 недели
**Бюджет:** по возможности 0 ₽, допустимо не более 300 ₽/месяц
**Основной режим работы:** аналитика + визуализация + прогнозирование

---

# 1. ГЛАВНАЯ ИДЕЯ ПРОЕКТА

VEMap — интерактивная аналитическая веб-платформа для визуализации изменения общественных настроений населения России по регионам во времени.

Основная идея:

1. Собираются данные из опросов.
2. Дополнительно данные могут поступать через Telegram-бота.
3. Ответы пользователей привязываются к региону.
4. На основе ответов рассчитывается количественный показатель настроения региона — **Mood Index**.
5. Mood Index отображается на карте России.
6. Пользователь может переходить между годами, за которые существуют данные.
7. Пользователь может сравнивать разные годы.
8. Пользователь может смотреть историю конкретного региона.
9. Пользователь может использовать режим прогнозирования.
10. Администратор управляет опросами, данными, публикацией и внутренней информацией.

Проект должен восприниматься не как «карта ради карты», а как **аналитическая система, где карта является главным интерфейсом исследования пространственно-временной динамики**.

---

# 2. ГЛАВНАЯ ЦЕЛЬ

Создать готовую к практическому использованию платформу, которая позволяет:

* анализировать настроение населения по регионам России;
* исследовать изменение показателей во времени;
* сравнивать регионы;
* сравнивать временные периоды;
* визуализировать результаты;
* работать с историческими данными;
* строить прогнозы на основе накопленной истории.

Приложение должно демонстрировать **готовность к аналитике и прогнозированию**.

При этом нельзя выдавать демонстрационный прогноз за гарантированно точный.

Качество прогноза должно зависеть от качества, количества и непрерывности исторических данных.

---

# 3. ЦЕЛЬ MVP

В рамках первой версии необходимо получить реально работающий продукт, а не демонстрационный набор отдельных экранов.

MVP должен содержать:

* красивую главную страницу;
* интерактивную карту России;
* регионы России;
* исторические данные по годам;
* временной ползунок;
* отображение Mood Index;
* карточку региона;
* таблицу данных;
* сравнение годов;
* график динамики;
* режим прогнозирования;
* публичную часть данных;
* административную панель;
* загрузку JSON;
* редактирование данных;
* Telegram-бота для сбора ответов;
* авторизацию администраторов;
* разделение публичных и внутренних данных.

# 4. ЧТО НЕ НУЖНО ДЕЛАТЬ В MVP

Следующие вещи НЕ являются обязательными и не должны усложнять проект:

* писать собственный картографический движок;
* создавать карту России с нуля;
* использовать внешний геокодер, если регион уже известен;
* использовать PostGIS без реальной необходимости;
* использовать deck.gl без реальной нагрузки, оправдывающей его применение;
* строить сложную нейросетевую модель прогнозирования только ради использования AI;
* создавать полноценную многоязычность на первом этапе;
* создавать сложную микросервисную архитектуру;
* разворачивать собственный картографический кластер в рамках MVP;
* подключать большое количество внешних API;
* реализовывать функции, которые не нужны пользователю или администратору.

**Главный принцип: сначала работающий продукт, затем усложнение.**

# 5. ТЕХНОЛОГИЧЕСКИЙ СТЕК

## Frontend

Использовать:

* React
* TypeScript
* Vite
* React Router
* MapLibre GL JS
* Recharts или Chart.js

* Zustand, если действительно потребуется глобальное состояние;
* Framer Motion для визуальных анимаций, если он не усложняет код.

Не добавлять библиотеку только ради её наличия.

---

## Backend

Использовать:

* Python
* FastAPI
* SQLAlchemy
* Pydantic
* PostgreSQL

Для авторизации:

* безопасное хеширование паролей;
* JWT или другой проверенный механизм сессий/токенов.

---

## Telegram

Использовать:

* aiogram

Telegram-бот должен получать ответы пользователей и передавать их backend.

---

## Forecast

Для MVP:

* scikit-learn;
* при необходимости statsmodels.

Модель прогнозирования должна быть отделена от основного backend-кода.

---

## NLP

NLP НЕ является обязательной основой проекта.

NLP применяется только там, где присутствуют свободные текстовые ответы.

Принцип:

```text
Числовой / структурированный ответ
        ↓
прямая нормализация и агрегация

Свободный текст
        ↓
NLP
        ↓
оценка тональности / эмоций
        ↓
агрегация
```

Не подключать RuBERT или transformers без реальной необходимости.

# 9. КАРТА

Использовать:

**MapLibre GL JS + GeoJSON.**

Не создавать карту вручную.

GeoJSON содержит геометрию регионов.

Справочник регионов содержит:

```text
region_id
region_code
name_ru
name_en
name_crh
federal_district
```

Для MVP GeoJSON и справочник регионов являются статическими данными проекта.

Внешний картографический API не обязателен.

# 10. ВАЖНОЕ РАЗДЕЛЕНИЕ

Не путать:

### Геометрия

```text
GeoJSON
```

отвечает на вопрос:

> Где находится регион и как он выглядит на карте?

### Данные

```text
Mood Index
```

отвечает на вопрос:

> Какое значение настроения имеет регион в конкретном году?

Их связь:

```text
region_id
      ↓
GeoJSON geometry
      +
year + mood_index
      ↓
MapLibre
```

# 11. ГЕОКОДИНГ

В MVP внешний геокодинг НЕ используется.

Пользователь сам указывает регион в рамках опроса.

Например:

```text
Ваш регион:

[ Москва      ]
[ Санкт-Петербург ]
[ Татарстан   ]
...
```

В БД сохраняется `region_id`.

Если в будущем появится источник данных, где регион неизвестен и вместо него присутствует адрес или координаты, можно добавить отдельный модуль геопривязки.

# 12. ВРЕМЕННАЯ МОДЕЛЬ

Основная единица времени:

```text
year
```

Диапазон потенциально:

```text
1–2026
```

Однако приложение **не должно искусственно создавать данные для каждого года**.

Если существуют данные только за:

```text
1
100
120
130
...
2026
```

ползунок должен отображать именно существующие годы.

Например:

```text
1 ─── 100 ── 120 ─ 130 ───────── 2026
```

Годы без данных не должны изображаться как существующие наблюдения.

---

# 13. ОСНОВНАЯ СУЩНОСТЬ — MOOD INDEX

Не использовать слово `sentiment` как единственное понятие всей системы.

Основной продуктовый показатель называется:

# Mood Index

Он является числовой оценкой состояния общественного настроения региона за конкретный временной период.

Базовая структура:

```text
region
+
year
+
Mood Index
```

Например:

```text
Москва
2026
Mood Index = 72.4
```

Шкала должна быть заранее формализована.

Рекомендуемый MVP-вариант:

```text
0 ─────────────────────────────── 100
```

где значение должно иметь однозначное документированное толкование.

ВАЖНО:

Не придумывать формулу Mood Index самостоятельно без отдельного согласования.

До утверждения формулы необходимо создать документ:

```text
docs/mood-index.md
```

с описанием:

* входных данных;
* нормализации;
* весов;
* формулы;
* диапазона;
* обработки пропущенных ответов;
* минимального размера выборки;
* версии методики.

# 14. МЕТОДИКА ДОЛЖНА ИМЕТЬ ВЕРСИЮ

    ↓

# 18. ПУБЛИЧНЫЕ ДАННЫЕ

Пользователь НЕ получает весь внутренний dataset проекта.

Публично предоставляется только специально разрешённая часть данных.

Публичный API должен самостоятельно фильтровать данные.

Нельзя делать:

```text
GET /all-data
```

и надеяться, что frontend просто скроет лишнее.

Скрытые данные не должны отправляться пользователю браузером.

# 19. АДМИНИСТРАТИВНАЯ ЧАСТЬ

Роли:

```text
USER
ADMIN
SUPER_ADMIN
```

## USER

Может:

* смотреть карту;
* менять год;
* смотреть данные;
* смотреть таблицы;
* смотреть графики;
* использовать прогнозирование;
* сравнивать периоды;
* выбирать регион.

Не может:

* редактировать данные;
* выгружать закрытый dataset;
* создавать опросы;

---

## ADMIN

Может:

* создавать опросы;
* редактировать опросы;
* загружать JSON;
* редактировать загруженные данные;
* просматривать внутренние данные;
* запускать обработку;
* отправлять данные на публикацию.

---

## SUPER_ADMIN

Дополнительно может:

* удалять опросы и данные;
* управлять администраторами;
* просматривать логи;
* управлять публикацией;
* выполнять административные операции;
* экспортировать полный dataset;
* управлять системными настройками.

# 20. ИМПОРТ ДАННЫХ

JSON не должен без проверки записываться непосредственно в рабочую БД.

Поток:

```text
Upload JSON
     ↓
Validation
     ↓
Preview
     ↓
Import
     ↓
Processing
     ↓
Aggregation
     ↓
Publish
```

При ошибке:

```text
Import failed
```

и пользователь должен увидеть понятное описание ошибки.

---

# 21. АДМИНСКАЯ РЕДАКТИРОВАНИЕ ДАННЫХ

Администратор должен иметь возможность:

* создавать;
* редактировать;
* добавлять;
* импортировать;
* просматривать;
* публиковать.

Удаление — только SUPER_ADMIN.

Желательно использовать мягкое удаление там, где это применимо.

---

# 22. АУТЕНТИФИКАЦИЯ

Пароли хранить только в виде безопасных хешей.

Никогда не хранить:

```text
password = "123456"
```

или любой другой пароль в открытом виде.

Администратор должен проходить аутентификацию.

Публичная часть сайта не требует аккаунта.

---

# 23. TELEGRAM-БОТ

Пользователь взаимодействует с ботом через:

```text
/start
```

При первом запуске:

1. пользователь создаётся/обновляется в БД;
2. сохраняется `telegram_user_id`;
3. сохраняется username как дополнительный атрибут;
4. определяется язык при необходимости;
5. пользователь проходит опрос;
6. пользователь выбирает регион.

Главным идентификатором Telegram-пользователя должен быть `telegram_user_id`, а не username.

# 24. ЕЖЕГОДНЫЙ ОПРОС

Но логика рассылки должна быть отделена от логики хранения ответов.

# 63. ГЛАВНЫЙ ПРОДУКТОВЫЙ ПРИНЦИП

VEMap должен отвечать пользователю на три последовательных вопроса:

### 1. Каково состояние?

```text
Какое настроение в регионе?
```

### 2. Как оно изменилось?

```text
Как настроение изменилось со временем?
```

### 3. Что может быть дальше?

```text
Как может измениться показатель в будущем?
```
